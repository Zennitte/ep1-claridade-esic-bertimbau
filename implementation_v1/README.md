# Implementation v1 — clareza de respostas e-SIC

Esta pasta preserva a primeira implementação do EP1 de PLN (ACH2118) para consulta em uma possível `implementation_v2`, especialmente na revisão do dataset. Ela reúne dados, divisões, código experimental, configurações, métricas, checkpoints e materiais de entrega. O pacote simplificado do modelo está separado em [`../deliverable/`](../deliverable/README.md) e foi publicado em [Zennitte/ESIC-BERT](https://github.com/Zennitte/ESIC-BERT).

**O [`plan.md`](plan.md) definiu a pipeline de desenvolvimento desta implementação.** Ele registra as etapas 0–8, o protocolo de avaliação, os critérios de decisão, os pontos de parada, o progresso e o diário de execução. Leia-o junto com os relatórios abaixo para reconstruir as decisões e os resultados.

## Visão geral

O objetivo foi classificar respostas e-SIC nas classes `c1`, `c234` e `c5`. O [`train.xlsx`](train.xlsx) tem 20.092 respostas rotuladas. O [`test1.xlsx`](test1.xlsx) tem 900 respostas sem rótulos, usadas na inferência final. O [`ep1-enunciado.pdf`](ep1-enunciado.pdf) descreve a tarefa da disciplina.

Para avaliar sem misturar respostas repetidas entre treino e validação, agrupamos textos após normalização conservadora de caixa e espaços. Separamos um holdout externo e, no restante, três folds agrupados. A referência foi TF-IDF com regressão logística. O modelo principal foi BERTimbau Base com uma cabeça de três classes. Após a busca e confirmação nos folds, escolhemos o início do texto até 512 tokens, taxa `2e-5` e a política de manter todos os rótulos originais, inclusive os conflitantes.

No holdout de 3.024 exemplos, o BERTimbau de auditoria obteve **45,966% de acurácia** e **44,523% de macro-F1**. O TF-IDF, treinado e avaliado nas mesmas linhas, obteve **45,437% de acurácia** e **45,056% de macro-F1**. A diferença de acurácia de 0,529 ponto percentual foi pequena (McNemar exato, `p = 0,590`). Depois dessa auditoria, o modelo definitivo foi treinado com todas as 20.092 linhas rotuladas, incluindo o antigo holdout. Logo, a métrica do holdout **não é a acurácia do checkpoint definitivo**. Como o conjunto externo `test1.xlsx` não tem rótulos, sua acurácia é desconhecida. Detalhes: [`reports/etapa5f_holdout_audit.md`](reports/etapa5f_holdout_audit.md), [`reports/etapa5f_tfidf_holdout_comparison.md`](reports/etapa5f_tfidf_holdout_comparison.md) e [`reports/etapa6_final.md`](reports/etapa6_final.md).

## Pontos de partida para uma v2 focada nos dados

- Há **316 grupos de texto normalizado com rótulos conflitantes**, totalizando 1.975 linhas. A ablação da etapa 5 comparou manter os rótulos, remover grupos conflitantes e conservar a maioria inequívoca. As alternativas não elevaram a acurácia no fold 1. O resultado não dispensa uma revisão de consistência da anotação; veja [`reports/etapa5_conflict_ablation.md`](reports/etapa5_conflict_ablation.md) e [`reports/etapa5_dataset_limit_diagnosis_examples.md`](reports/etapa5_dataset_limit_diagnosis_examples.md).
- `c234` teve recall de **24,131%** no holdout BERT. O diagnóstico do fold 1 também encontrou um gap de **13,88 pontos percentuais** entre treino e validação. Os exemplos documentados podem orientar a revisão de critérios de rotulagem, ambiguidade e eventual coleta de contexto adicional.
- Uma v2 precisa de avaliação independente nova. O holdout da v1 já foi consultado e incluído no treino final. Seus índices servem para reproduzir a v1, mas não constituem teste inédito para novas decisões.

## Organização e reprodução

`configs/` guarda parâmetros, `data/` manifestos e divisões, `src/` código, `runs/` logs e métricas, `models/` checkpoints, `reports/` análises, `outputs/` entregas e `tmp/` intermediários. As planilhas originais estão na raiz desta pasta. [`.gitignore`](.gitignore) documenta o que ficava fora do Git da v1.

No repositório histórico [ep1-claridade-esic-bertimbau](https://github.com/Zennitte/ep1-claridade-esic-bertimbau), os 20 arquivos `model.safetensors` são armazenados por **Git LFS**. Após clonar, instale/habilite Git LFS e execute `git lfs pull` antes de usar os checkpoints. Os dados, resultados e demais arquivos do snapshot são publicados, exceto `.venv/`. O modelo simplificado permanece no repositório separado [ESIC-BERT](https://github.com/Zennitte/ESIC-BERT).

A [`.venv/`](.venv/) foi movida com o snapshot, mas ambientes Python podem registrar caminhos absolutos. Após a mudança de diretório ou em outra máquina, recrie o ambiente conforme [`ENVIRONMENT.md`](ENVIRONMENT.md) e [`requirements.lock.txt`](requirements.lock.txt). Execute os scripts a partir de `implementation_v1/` para que os caminhos relativos continuem coerentes.

Este README é o mapa do arquivo histórico. Para comandos, ressalvas, correções e decisões em ordem cronológica, consulte [`plan.md`](plan.md) e os relatórios de cada etapa.
